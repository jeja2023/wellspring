# 清源版本发布流程（个人开发阶段）

## 版本与“未发布”

- `[未发布]` 是当前已经修改、尚未归入具体版本的工作区变更，不表示不能发布。每次形成小版本时，把对应条目整理到 `[版本号] - 日期`，并记录验证、升级和限制；新的变更再写入新的 `[未发布]`。
- `0.0.x` 为开发验证版本，可在本地编号、打包和使用虚构数据测试；不表示生产上线或正式业务验收。
- `0.1.0`、`1.0.0` 的使用应分别符合项目已确定的 MVP 和生产批准条件，不能以编号代替验收。
- 产品版本与方案文档 v2.5.0、开发规范版本、数据库迁移编号分别管理；它们不要求相同。

## 当前机制及实际限制

当前产品版本为 `0.0.7`（2026-11-12），数据库迁移 head 为 `0028`。本次范围、实际验证与升级方式见 [0.0.7 版本说明](0.0.7-版本说明.md)。源码归档名为 `wellspring-0.0.7-source.zip`，其配套摘要为 `.zip.sha256`；前端包/锁文件、后端 API 和部署默认应用标签须保持同一产品版本。历史 `0.0.6` 及更早版本的文档证据、Git 提交/标签及源码包不随当前版本号改写。`0.0.7` 沿用 `0028`，没有新增数据库迁移；本次只更新版本、文档和源码制品，Git 提交/标签未自动创建。

项目使用本地 Git 仓库管理源码，不配置远程仓库。以 `0.0.2` 当前工作区作为首次提交并标记 `v0.0.2`；更早的 `0.0.0`、`0.0.1` 仅有更新日志，不能伪造历史 Git 提交。既有源码包先于仓库初始化生成，不含此后新增的 Git 管理文档。当前没有托管平台 Release 或远程 CI 结果，不能表述成已推送或生产部署。

## 个人开发版发布步骤

1. 确定本次范围，完成功能、必要测试和缺陷处理，记录未实现与风险。
2. 更新前端包与锁文件、后端 API、部署镜像引用和文档中的产品版本；不修改历史条目。
3. 停止旧版本，备份开发数据库；在隔离副本验证旧版升级迁移和全新安装，记录不可逆风险。正式环境的备份恢复单独演练。
4. 运行前端测试／类型检查／构建、后端测试及迁移一致性检查；涉及权限、幂等和数据流水的变更包含正反向用例。
5. 将更新日志 `[未发布]` 中属于本次的条目归入版本，写明日期、测试环境／结果、升级方法和局限。
6. 在项目根目录运行 `python scripts/build_source_release.py`，生成版本化源码归档和 SHA-256；脚本按白名单打包，不包含数据库、`.env`、密钥、`node_modules` 和虚拟环境。使用可信渠道保存摘要；摘要并非数字签名。
7. 将源码包视为开发交付物；本地提交和标签由 Git 记录；如果未来需要远程 Release，应先单独配置并确认可信仓库。不要事后虚构历史提交或验证结果。

## 生产 Docker 离线发布

需另行完成固定来源／摘要的镜像构建、全量依赖锁、SBOM／许可证／漏洞审查、离线包核验、目标平台联调、数据库与文件备份恢复、权限安全测试和上线批准；详见 [离线部署说明](../deploy/offline/README.md)。无证书 HTTP 的网络风险需明确评估。当前本地源码包不包含可直接生产部署的镜像。

## 本地 Git 日常操作

```powershell
git status
git log --oneline --decorate
git diff
git add <本次需要纳入的文件>
git commit -m "描述本次变更"
git tag -a v0.0.x -m "开发验证版本"
```

提交前检查暂存文件和差异，禁止将密码、会话令牌、真实数据、数据库、私钥和运行日志纳入 Git；`.gitignore` 不会自动移除已经跟踪的文件。数据库、对象文件及 Git 历史需要独立备份，本地仓库不是异地备份。恢复代码前先确认未提交修改和数据库迁移，不对用户工作执行未经确认的破坏性回退。
