### 术语约定

- **必须／禁止**：强制要求；不满足时不能合并或不能通过对应门禁。
- **应**：默认要求；例外必须记录理由、风险、责任人、有效期和补偿措施。
- **可**：允许的实现选择；仍需满足安全、契约和验收要求。
- **主体**：当前登录用户、服务账号或经批准的后台任务身份。
- **授权范围**：主体在当前时刻能够访问和执行的组织、辖区、案件／专案、字段、附件及操作范围。
- **正式事实**：经过规定来源、审批或人工核验后进入业务事实层的数据；草稿、候选、模型推断和暂存数据不属于正式事实。

## 1. 目的、适用范围与执行方式

本规范为首期及后续获批范围提供统一的界面、交互、接口、数据、安全、测试和交付标准。新功能、重构、缺陷修复和依赖升级均适用；原型、设计稿、实现、自动化检查及验收用例应使用同一术语和规则。开发验证版本仅允许虚构数据，不得用于实际业务。

**强制程度：**“必须／禁止”是合并或验收要求；“应”是默认要求，确有合理例外须记录理由、风险、责任人和补偿措施；“可”供选择。本文件的具体组件尺寸、分页参数和接口示例为项目建议基线，须通过设计及技术评审冻结。法律、保密、主管部门制度及经批准的总体方案高于本文件；冲突或未明确时，先升级给相应负责人，不由开发人员猜测业务规则。

1. 功能开始前，任务必须关联需求、设计稿或原型、字段与状态、权限矩阵、异常路径及验收标准；跨部门业务需明确负责人和确认版本。
2. 影响敏感权限、法律决定、证物计量与审批的数据规则，未核准前只能实现无真实数据的验证，不得当成生产规则发布。
3. 新增或变更规范由提出人说明影响、迁移计划、兼容性和验证证据，经产品、技术及受影响责任人评审后版本化。旧页面按批准计划整改，不以草案生效宣称存量已合规。
4. 项目使用 Vue 3 + TypeScript、FastAPI、SQLAlchemy/Alembic 与 PostgreSQL 的方案基线；具体版本、组件库和目标环境经阶段 0 验证冻结。不得擅自改变技术栈或引入新的运行时服务。

### 1.1 开发前检查和修改边界

每次新增功能、缺陷修复、重构、页面调整、接口扩展、文档处理或依赖升级开始编码前，必须完成以下检查并记录在工作项或合并请求中：

1. 阅读本规范、总体方案、相关业务规则、设计稿、数据字典和现有实现；外部参考文档只作为改进依据，不得把其中的项目名、目录、脚本、组件类名或业务规则直接复制到 Wellspring。
2. 使用代码搜索确认已有页面、路由、服务、查询、样式、组件、任务和测试；已有能力能够满足需求时必须复用或扩展，禁止并行建立第二套相同体系。
3. 写明影响范围：前端页面、组件、路由、后端 API、领域服务、数据库、迁移、文件上传、对象存储、任务、AI／OCR、权限、审计、日志、配置和测试。
4. 涉及 UI 时先确认设计令牌、共享组件和同类页面；涉及文档处理、OCR、PDF、导入或 AI 时先确认统一处理底座和任务协议；涉及权限时先确认权限矩阵和撤权行为。
5. 不破坏现有已验收行为，不做与本需求无关的重构、重命名、依赖替换和目录迁移；如果现有结构直接阻碍正确实现，应在任务中说明原因、影响、迁移和回归范围。
6. 禁止提交临时代码、调试按钮、测试页面、未使用变量、死代码、无效注释、硬编码测试数据、临时控制台输出和未注册的功能开关。
7. 需求不完整时，采用与当前架构和已批准规则一致的最小方案；不能自行推断法律状态、权限范围、保留期限、计量规则或生产指标。需要决策时记录问题、选项、责任人和冻结日期。

开发完成后，合并请求必须说明复用过的既有能力、未做的无关改动、兼容性、回退方式和仍待确认的事项。小改动也必须满足安全、权限、错误处理和测试要求，不能以改动行数少为由跳过门禁。

## 2. 信息架构与页面模式

### 2.1 导航与页面层级

- 固定产品简称“清源”，系统全称“清源·禁毒全流程协同平台”，英文品牌 Wellspring；使用方案确认的业务副标题。导航名称应与权限及业务术语一致，避免同一功能多个名称。
- 日常业务采用左侧主导航、顶部上下文栏和右侧内容区。顶部至少显示当前页面、组织和账户入口；详情、编辑等多级页面提供面包屑或明确返回入口。返回列表时保留用户原筛选、页码和排序，授权失效或数据变化时重新查询。
- 菜单根据服务端授权呈现；无权限的直接访问仍由服务端拒绝。未建设模块不得显示成可用功能；确需展示规划模块时明确标注“建设中”，不显示虚构统计或操作结果。
- 工作台只展示必要的待办和指标；每项标明口径、数据权限范围和更新时间。无权查看时不通过数字、占位文案或错误差异泄露对象存在性。
- 页面分为工作台、列表、详情、表单／向导和处理工作台。避免在一个页面塞入无关流程；复杂业务拆分成清晰步骤并保留进度。

### 2.2 桌面布局与适配

- 首期以目标单位批准的桌面浏览器、分辨率和缩放级别为准，设计评审必须记录支持矩阵。建议以 1440×900 和 1366×768 为设计检查点，并测试 200% 浏览器缩放；这些是设计测试基线，不代表目标环境已验收。
- 内容区域使用响应式宽度，列表、表单和文字不应因窗口缩窄而重叠或被遮挡。窄视口可收起侧栏；表格优先允许局部横向滚动，不得让整个页面因表格无意横向溢出。具体移动端支持范围另行确认。
- 建议侧栏宽 224–240 px、顶部栏高 64 px、页面外边距 24–32 px、模块间距 16–24 px；采用 4 px 间距网格（4／8／12／16／24／32）。同一层级的模块对齐，表单和表格使用一致的密度。
- 同一工作区通常只保留一个主要操作；页面标题下提供简短说明，危险操作与普通提交分组。高频操作、状态和待办应在首屏可见，不以大面积装饰挤占业务空间。
- 新增页面须提供加载、空、无结果、无权限、失败、成功以及必要的部分成功状态；长页面和弹窗应明确保存、取消与返回行为。

## 3. 视觉基础与设计令牌

### 3.1 品牌色和语义色

| 令牌 | 建议值 | 用途 |
|---|---|---|
| `color-brand` | `#153B5B` | 导航、主操作、关键层级 |
| `color-accent` | `#0E7770` | 协同、完成、正向状态 |
| `color-page` | `#F4F7FA` | 页面背景 |
| `color-surface` | `#FFFFFF` | 工作区、卡片和表单背景 |
| `color-border` | `#D8E1EA` | 常规边框与分隔 |
| `color-text` | `#17324D` | 正文 |
| `color-warning` | `#A65F00` | 待处理、预警文字与图标 |
| `color-danger` | `#B42318` | 危险、异常文字与图标 |

颜色在主题令牌中集中维护，不在业务页面散落硬编码；白底、浅色底、禁用、悬停、焦点、选中和深色导航分别验证对比度。普通正文以 WCAG 2.2 AA 的 4.5:1 为目标，大文字及必要非文字状态以适用的 3:1 为目标；若组件或环境不适用，记录依据及等效方案。不得仅靠颜色表达状态：使用文字，必要时配图标、图案或说明。

### 3.2 字体、形状与图标

- 使用系统可用的中文无衬线字体，建议正文 14 px、辅助文字不小于 12 px、页面标题 24–28 px、模块标题 16–18 px，行高约 1.5；不得以缩小字号替代布局调整。
- 常规控件、卡片采用统一圆角和边框；阴影仅用于浮层及层次区分，避免大面积渐变、霓虹、地图大屏或装饰图。图标来自统一、许可已审核的图标集，单独图标按钮必须有可访问名称和悬停说明。
- 日期、数字、状态、图标和空状态插画统一组件或令牌。设计稿及测试数据标明“示意数据，禁止用于生产”，使用不可识别的虚构数据。

## 4. 通用组件与交互规范

### 4.1 按钮与操作

| 类型 | 使用原则 | 示例 |
|---|---|---|
| 主按钮 | 页面或弹窗中最重要的一个动作 | 保存、提交审批 |
| 次按钮 | 同级辅助动作，视觉弱于主按钮 | 返回、取消、重置 |
| 文本按钮 | 表格行内低风险操作；保持可识别和足够点击区域 | 查看详情 |
| 危险按钮 | 撤销、作废、销毁等经授权动作，使用危险语义 | 提交销毁审批 |

- 按钮使用明确动词及对象，避免“确定”“操作”等脱离上下文的词；统一高度、内边距、图标间距、圆角、悬停、聚焦、加载及禁用样式。建议常规高度 36–40 px，具体由组件库和目标设备评审冻结。
- 提交后立即显示进行中状态并阻止重复点击，保留请求结果；前端禁用不是幂等保证。接口超时或响应丢失时先查询操作状态，不提示用户盲目重复提交。
- 无权限操作按权限与防泄露设计决定隐藏或禁用；禁用时提供不泄密的原因。不能仅依赖隐藏或禁用保护接口。
- 不可逆或影响重大的操作必须使用明确的二次确认，说明对象、范围、后果及是否可撤回；确认按钮写明动作。关键审批、证物操作还须满足批准的角色分离、版本和依据校验，普通确认弹窗不能替代审批。

### 4.2 表格与列表

- 列表页通常包含标题和说明、权限内主操作、筛选区、结果区、分页及结果状态。列表读取由服务端先授权，再过滤、排序和分页。不得先拉取全量数据到浏览器再做权限过滤。
- 表头使用业务名称和必要单位；文本左对齐，数量和金额等数字右对齐，状态使用文字标签。唯一标识或长内容可安全截断，允许查看完整内容的前提是具备授权；禁止通过 `title`、隐藏列或 DOM 泄露无权字段。
- 默认展示必要字段；敏感字段由服务端按权限输出或遮盖，列设置不得绕过字段权限。行操作按频次排序，过多时折叠；批量操作明确选中范围、逐项权限、失败项及结果，不得默认跨页全选。
- 支持加载骨架或进度、首次无数据、筛选无结果、请求失败及重试。筛选条件变化时回到第一页；排序需有稳定的唯一键作为次排序。刷新或返回后以服务端当前权限和数据为准。
- 行点击、勾选、排序及操作须支持键盘和屏幕阅读器；操作按钮不得被行点击事件误触。固定列、横向滚动和大字号缩放不得遮盖操作或表头。

### 4.3 分页、筛选与排序

1. 所有业务列表必须服务端分页并限制每页最大值；默认第 1 页、每页 20 条，可选择 20／50／100 条，最大 100 条。超限或无效参数返回明确校验错误，不静默全表读取。大数据及频繁变化列表可采用游标分页，契约需声明其行为。
2. 页码分页示例使用 `page`、`page_size`、经白名单验证的 `sort` 和 `order`；数据库排序必须稳定，例如 `created_at DESC, id DESC`。禁止将客户端排序字段直接拼进 SQL。
3. 接口在授权、过滤后分页。只有统计本身经授权且不存在侧信道风险时才返回 `total`；无法安全或高效统计时返回 `has_more` 并采用适合的分页控件。受限碰撞等场景不得通过页数、总数、状态码或响应差异泄露未授权信息。
4. 搜索条件、状态和排序通过明确的 API 契约传递；避免在 URL、浏览器历史、日志或统计中保留敏感字段。查询条件长度和复杂度设上限，关键敏感检索需审计。
5. 删除、撤权或其他人修改造成当前页无数据时，重新请求合法的上一页并提示数据已变化；跨页选中应明确是“本页”还是经授权的指定范围。导出采用单独授权和后台任务，不用扩大 `page_size` 代替。

### 4.4 输入框、表单和下拉框

- 每个字段有可见标签；占位文字仅作示例，不能代替标签。必填标识、业务单位、格式、长度、来源和帮助说明在录入前可见；错误紧邻字段并用文字说明如何修正。
- 字段分组符合业务流程，相关项相邻。编辑表单加载现有版本，取消或离开含未保存更改的页面需提示；提交失败不清空输入。保存草稿与正式提交的要求分别说明。
- 前端校验用于即时反馈，后端独立完成类型、长度、范围、业务规则、授权和版本校验。空值、空字符串、缺失与零应按字段语义区分；不得仅用前端禁用控制正式状态。
- 证物质量以克为核算单位，按批准精度使用十进制定点及 `Decimal`；输入不得通过 JavaScript 浮点计算余额，传输使用十进制字符串。初期建议最多六位小数，精度和单位换算须经业务核准后冻结；超出精度报错，不静默截断或四舍五入写账。
- 日期选择器明确时区及日期／时间含义；无法确定的时间不得伪造为当天零点。单位、编号、姓名及来源等字段遵循数据字典，不以显示格式充当唯一身份依据。
- 下拉选项使用经授权且当前有效的数据源；区分单选、多选、可搜索和可清除。长列表分页或按需搜索；选项加载、无结果、失败和已失效值均有提示。禁止将未经授权的完整选项列表发送到前端。
- 输入框、下拉框、日期、复选／单选、开关应统一尺寸、边框、提示、错误和禁用样式，并支持键盘、焦点可见、可访问标签与错误关联。

### 4.5 提示、警告、通知和弹窗

| 类型 | 适用场景 | 持续方式与要求 |
|---|---|---|
| 字段错误 | 单个输入不符合要求 | 保留至修正；关联字段和错误文本 |
| 轻提示 | 非关键、已完成的小操作 | 短暂显示；内容不包含敏感数据，不能作为唯一结果记录 |
| 页面提示／横幅 | 持续影响当前页面的状态或风险 | 留在上下文中，说明影响及可用操作 |
| 警告 | 潜在风险、过期或异常待处理 | 用文字说明原因、影响和处理路径，不用颜色单独表达 |
| 通知中心 | 需要稍后处理的待办或任务结果 | 服务端按权限生成，支持已读及跳转；不得泄露无权详情 |
| 确认弹窗 | 需用户主动确认后果的操作 | 明确对象、影响、取消与确认；危险动作明确命名 |

- 成功提示必须与真实结果一致；异步任务创建成功只能说“任务已提交”，不能说“处理完成”。部分成功展示成功、冲突、失败数量及可查看的逐项结果；不以绿色提示掩盖错误。
- 重要错误和审批结果不得仅靠自动消失的 toast；通知与待办的状态变更由服务端维护并受权限约束。消息文案使用中文、简洁、中性、可执行，不暴露堆栈、SQL、令牌或他人敏感资料。
- 弹窗打开后焦点进入弹窗，键盘焦点限制在弹窗内，关闭后返回触发点；允许安全取消，不阻塞必要的错误恢复。涉及高风险操作时二次确认仍须受后端审批与职责分离限制。

### 4.6 状态、反馈与无障碍

状态由后端返回明确代码，前端用集中维护的映射展示中文名称、语义和可用操作；未知状态显示“未知状态”并记录诊断，不默认为成功。状态变化必须刷新记录和版本，不能靠前端猜测合法流转。

所有交互支持键盘访问和可见焦点；语义化标签、表头、对话框和状态消息应正确供辅助技术识别。异步错误使用合适的 `role=alert` 或实时区域，避免反复打断。检查文字对比度、200% 缩放、表格滚动及仅键盘操作；最终支持范围与辅助技术环境由建设单位确认。

## 5. 业务流程与数据呈现

### 5.1 通用流程

- 每个流程实现前形成状态转换表：当前状态、动作、目标状态、操作者、权限、前置条件、审批、对象版本、异常及审计。非法转换由服务端拒绝；历史事件追加保留，不用覆盖状态代替事实。
- 申请、审批、执行、复核按批准矩阵分离；不能自己批准自己的关键申请，也不能以页面隐藏按钮代替服务端检查。审批过期、撤销、对象或依据变化时，必须重新核验。
- 案件“关联”和“并案”是不同关系；关系类型与生效状态分开，撤销关系不撤销案件。人员的措施、执行、检测、管辖与提醒分开建模，日期到期不自动认定法律状态改变。
- 证物显示随机不透明标识、所属授权范围、对象状态、当前保管、计量来源和可追溯事件；二维码不得包含姓名、案件详情或敏感直链。交出、接收、拒收、异常、分样、消耗、退样、盘点和销毁按批准流程分别记录，审批不能提前扣账。
- 导入须展示来源、模板版本、摘要、暂存、差异、逐行结果和冲突；正式确认重新检查授权及目标版本，禁止静默覆盖权威来源。AI 输出必须明确为待核验草稿，展示原文定位、版本与人工确认，未经确认不得写正式事实。

### 5.2 数字、时间和脱敏

- 展示时间格式统一为 `YYYY-MM-DD HH:mm:ss`，页面明确所用时区；日期字段与时间戳分别建模。建议存储 UTC 时间戳，并在展示层转换为经批准的业务时区；记录原始时区或来源时间的场景不得丢失其语义。
- 列表与详情的单位、精度、空值文案一致。金额、重量、数量使用各自的数据类型和校验，不混加；展示舍入不改变原始数据或流水。
- 身份证件、手机号、地址及其他敏感信息按照字段权限在服务端最小化返回或遮盖；复制、导出、搜索摘要、历史版本和错误信息使用同样规则。数据脱敏不等于授权。

## 6. 前端工程规范

1. 按业务域拆分页面、组件、API 客户端、类型、状态映射及测试；通用控件封装于共享设计系统，业务规则不能复制到多个组件。组件库须经许可证、无障碍、离线构建和安全评审，选型冻结后统一使用。
2. 启用 TypeScript 严格模式；网络数据先按契约校验并转换，避免不受控 `any`、非空断言和无意义类型转换。禁止前端直接访问数据库、对象存储管理端或持有服务端密钥。
3. API 客户端集中处理认证、超时、错误映射、关联 ID 和会话失效；业务页处理业务语义。登录态及敏感缓存遵循已批准的认证方案；不得将长期凭据放入浏览器持久化存储。页面注销、账号禁用及授权撤回后重新校验，不能依赖旧缓存继续展示敏感数据。
4. 不使用不可信 HTML；确需富文本时采用经审查的清洗与输出编码策略。上传文件名、AI 输出、导入内容和服务端错误均视为不可信输入。
5. 长列表使用服务端分页，避免把大量数据和敏感字段放到 DOM；请求取消或竞态发生时，以最新有效请求结果更新界面。路由、参数、筛选、状态和权限错误有清晰反馈。
6. 日志和浏览器监控不记录令牌、密码、完整身份证号、案情、原文或模型输入。分析指标采用最小化数据，关闭未经批准的公网遥测。

## 7. 后端、接口与数据库规范

### 7.1 分层与事务

- 路由层负责协议、参数及响应；应用／领域服务负责业务规则、授权编排和事务；数据访问层封装查询；基础设施负责数据库、对象存储和外部服务。禁止路由或 Worker 绕过领域规则直接改写正式业务表。
- 输入、输出使用明确的 Pydantic 模型；不直接将 ORM 内部对象和敏感字段暴露给客户端。配置来自受控环境及密钥管理，不硬编码账号、令牌、证书和真实数据。
- 服务端从认证上下文解析主体、组织、有效授权和版本，不能信任客户端提交的 `org_id` 或角色。读取、写入、导出、附件、搜索、统计、后台执行与结果交付均独立校验权限。
- 关键业务写入、状态变更、关联任务和本地审计必须同事务提交；任何一步失败则回滚。外部对象写入或通知不可与数据库天然原子提交，须采用持久化状态、幂等、补偿、对账及告警机制。
- 并发更新使用版本号、条件更新或数据库锁，校验失败返回冲突，不静默覆盖；操作依据、申请、审批、执行人和时间按业务规定记录。

### 7.2 API 约定

- 正式 API 使用统一版本前缀（建议 `/api/v1`），资源名称及状态代码稳定，契约通过 OpenAPI 和测试版本化。现有开发接口 `/api` 尚未符合此目标，迁移需制定兼容及下线计划，不静默改变。
- 常规响应结构和错误格式由项目统一；建议错误包含稳定 `code`、安全的 `message`、字段错误（如适用）及 `request_id`。不得返回 SQL、堆栈、内部地址或敏感原文。HTTP 状态按语义使用：400／422 参数无效、401 未认证、403 无权、404 不存在或按防泄露策略统一响应、409 版本／状态冲突、429 受限、5xx 服务异常；受限碰撞等场景按批准的防泄露契约处理。
- 列表契约示例（仅在总数可安全返回时）：

```json
{"items": [], "page": 1, "page_size": 20, "total": 0, "request_id": "示例关联标识"}
```

无权或不适合返回总数时，契约使用 `items`、`has_more` 和下一页游标等明确字段。字段名、空值、最大长度、枚举、日期、版本、错误码和兼容性必须写入接口文档；敏感查询禁止在示例中使用真实数据。
- 会产生重复副作用的写请求使用客户端生成的幂等键，并在授权范围内与操作类型、请求摘要和结果绑定；并发重复仅生效一次，相同键不同请求返回冲突，重试可查询原结果。有效期及回收策略由业务与运维批准；不要将前端防重复点击视为幂等实现。
- 查询字段、排序和过滤条件使用白名单及参数绑定；分页上限、请求体、上传大小和超时在服务端限制。耗时导入、OCR、导出进入持久化任务，不占用长请求或数据库长事务。

### 7.3 数据模型、迁移和计量

- 核心实体、关系、约束、索引和来源写入数据字典。字段必须明确类型、精度、是否可空、唯一范围、来源、更新权限、敏感级别及保留策略；关键不变量同时由服务和数据库约束保障。
- 使用 Alembic 版本化迁移；生产不得手工漂移 DDL。迁移需评审锁表、数据量、兼容性、前向修复、恢复点及回退方案；破坏性迁移不保证可用反向 DDL 无损恢复。发布先验证备份，分步扩展／迁移／切换／清理。
- 正式事实、流水、审计和来源记录不得通过普通删除或覆盖抹去；更正、冲正及撤销应引用原事件、说明原因和审批，检查后续影响。附加唯一键、检查约束和并发控制，以保证重复操作和负余额不发生。
- PostgreSQL 运行角色与迁移、备份、审计、分析角色分离；敏感表按批准矩阵设计 RLS，非超级用户、非表所有者、无 `BYPASSRLS`。事务局部身份上下文缺失默认拒绝，并测试连接池回收、异常和多角色策略组合。RLS 是纵深防御，不替代应用授权或对象存储授权。

### 7.4 后台任务、文件和 AI

- 同一业务库持久化任务，业务事件、任务及审计同事务创建；Worker 短事务领取，使用租约、递增代次、心跳与重试。接管后旧 Worker 不得提交结果；正式结果、任务状态和审计同事务完成，并通过业务幂等约束防重。执行和交付前重验授权及输入版本。
- 文件使用私有存储，经过暂存、类型及恶意内容检查、资源限制、摘要核对和元数据提交后才可引用；下载、预览、导出按对象关联与当前权限校验。缺失或摘要不符时停止使用并告警，不伪装为空文件；清理前检查引用、保留与冻结。
- OCR／模型服务最小权限、限定资源和网络边界；文书内容视为不可信输入。草稿保存模型、提示模板、解析器版本、原文摘要与字段定位；人工核验绑定原文、草稿和目标版本，变化后重新核验。不得把模型自报置信度当作真实准确率。

### 7.5 文档处理、OCR 和 PDF 共享底座

文档处理、OCR、PDF、导入和 AI 解析属于跨业务基础能力，必须统一协议和任务模型，业务模块只调用底座，不得在多个路由或页面中复制解析链路。

1. 文本型 PDF、Word、Excel、TXT 等文件优先走文本抽取；无文本层 PDF、扫描件和图片才进入 OCR；文件类型不能只依据扩展名判断。
2. 统一处理结果至少包含原文件标识、对象版本、页码、文本、段落／块／行、坐标（如适用）、语言、解析器／OCR 引擎版本、参数、质量标记和错误信息。
3. OCR／PDF 处理服务与业务 API 解耦，通过受控任务协议调用；业务代码不得直接依赖某个模型目录、命令行工具、第三方 SDK 内部对象或本地临时路径。
4. 统一任务状态至少覆盖 `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCEL_REQUESTED`、`CANCELLED`；保存重试次数、失败原因、输入摘要、授权范围、处理者和输出引用。取消不抹去已生效结果。
5. 处理服务必须提供健康检查、资源限制、超时、页数／文件大小上限、失败隔离和清理机制；普通业务不能因为 OCR／AI 服务故障而不可用。
6. 原文、OCR 结果、人工修订、结构化候选和正式事实分层保存；人工修改后记录修订者、时间、依据和版本，禁止用结果覆盖原件。
7. 需要展示原文时使用原页预览或稳定的页码／坐标引用；导出、下载和发送到业务模块必须再次校验当前权限并写入审计。
8. 新增具体处理引擎前，必须评估离线安装、许可证、模型摘要、资源需求、提示注入、样本质量、回归评测和升级回滚；不能因为引入一个库就改变全项目的文档处理方式。

## 8. 安全、权限和审计

### 8.1 认证与授权

认证方式、会话时长、失败处置、统一身份接入、撤权时限和紧急访问由安全及业务负责人批准。生产使用 HTTPS、命名账号和可撤销服务端会话，密码使用成熟的加盐自适应哈希；禁止共享业务账号和默认生产凭据。登录限速、账号停用、会话撤销及权限变更均需测试。

权限矩阵至少覆盖主体、功能动作、组织范围、案件／专案授权、敏感字段、有效期、审批、拒绝条件和审计。账号禁用、授权撤销及到期优先于宽泛角色；用户只能看到其授权范围内的必要人员字段和事件，关联到一个可见案件不自动赋予全部历史权限。运维管理员不因系统管理而获得业务数据访问权。

### 8.2 审计、日志和隐私

- 登录、授权变更、敏感查询、关键业务写入、证物计量及交接、导入、AI 人工确认、文件访问、导出、系统配置和运维等按批准策略留痕。记录主体、动作、对象、时间、结果、来源、关联任务／审批和版本摘要，避免复制敏感原文。
- 普通业务日志不能作为受保护审计的替代。关键审计随业务事务提交；运行角色不得更新／删除审计，另向独立受保护目标归集，归集失败需持久化重试与告警，积压达到批准阈值时限制相应敏感操作。
- 开发、测试、演示使用虚构或经批准脱敏的数据；禁止未经批准把真实数据带出安全域。异常、监控、截屏、测试报告和工单按同样要求处理。

## 9. 质量门禁与研发流程

### 9.1 需求、设计及代码评审

| 门禁 | 必须具备的证据／条件 | 责任人 |
|---|---|---|
| 需求准入 | 范围、角色权限、字段、状态、异常及验收标准；涉及法律或业务规则提供批准依据 | 产品＋业务，敏感项由法制／安全参与 |
| 设计准入 | 页面原型、组件状态、接口及数据字典；高风险流程有职责分离、并发、审计和恢复设计 | 设计＋前后端负责人 |
| 代码合并 | 关联任务、同行评审通过、自动化检查通过、迁移和风险说明；不得提交密钥或真实数据 | 作者＋至少一名非作者评审人 |
| 测试准出 | 需求与用例可追溯，核心、异常、越权及数据一致性测试通过，缺陷按批准规则处理 | 测试＋业务／安全 |
| 发布准入 | 签字的范围、制品、变更与回退、备份恢复、安全测试、运维交接和发布批准齐全 | 发布负责人＋相关责任人 |

- 分支保护、强制评审和 CI 必须在业主可控仓库中配置；不得由作者自行绕过。紧急修复须记录授权、影响、补测和事后评审。
- 提交／合并请求说明问题、实现、影响、验证、迁移、权限和回退；前端变化附关键状态截图或原型链接。范围变化时更新需求、文档与测试。
- 重大例外须记录风险接受人和整改期限，不能用例外绕过必须履行的业务审批、法律要求、越权缺陷或账实完整性要求。

### 9.2 自动化门禁基线

CI 应在干净环境执行以下检查并保存日志与报告；未配置的项目视为待建设，不得标记为已通过。

1. 前端依赖锁文件一致性、类型检查、代码格式／静态检查、单元测试和生产构建；关键页面的可访问性与端到端测试按风险纳入。
2. 后端依赖锁文件一致性、格式／静态检查、类型检查、单元及 API 集成测试；迁移在空库执行并检查模型差异，受影响变更验证升级及恢复方案。
3. PostgreSQL 集成测试使用与生产边界一致的非特权角色，覆盖 RLS、权限、事务、并发及连接池上下文；SQLite 测试不能替代此项。
4. 依赖、许可证、漏洞、密钥和制品扫描；输出 SBOM 和来源摘要。阻断阈值、修复时限和例外审批由安全负责人冻结，不以扫描通过代替安全评审。
5. 覆盖率阈值根据项目风险与基线由测试负责人确认；不得为追求数字增加无业务意义的测试。涉及越权、计量、审批及正式事实的关键路径必须有正反向用例。

当前仓库现有可执行检查为 `backend` 下 `python -m pytest -q`、`python -m alembic check` 和 `frontend` 下 `npm run build`；自动 CI、完整依赖锁、静态检查、PostgreSQL 权限测试等尚待建设。真实门禁应通过仓库配置执行并留存结果，而不是仅在本文列出命令。

## 10. 测试与验收规范

### 10.1 测试层次与数据

- 单元测试覆盖可独立验证的计算、状态和规则；API／数据库集成测试覆盖认证、事务、迁移、约束、版本及错误；端到端测试覆盖关键用户流程及界面反馈。
- 使用可重复、隔离的虚构数据和固定时钟／可控外部依赖；测试不得依赖共享生产资源、测试执行顺序或外网。测试结束清理测试资源，保留必要的脱敏证据。
- 每个需求至少关联正向、异常、权限反向及验收用例；测试报告记录环境、数据规模、版本、结果、缺陷与复测结论。真实业务、权限及性能阈值以阶段 0 批准基线为准。

### 10.2 必测场景

| 范围 | 最低覆盖 |
|---|---|
| 界面与组件 | 加载、空、无结果、失败、重试、成功、部分成功；键盘、焦点、对比度、缩放、表格横向滚动、字段错误与危险确认 |

| 认证与授权 | 未登录、禁用、过期、撤销、跨组织／跨案件、敏感字段、导出和附件；多角色叠加及服务端直接调用 |
| 业务流程 | 合法和非法状态转换、退回、拒绝、撤销、过期审批、职责分离、版本冲突、幂等与并发 |

### 10.3 缺陷与退出标准

缺陷记录重现步骤、环境、实际／预期、证据、影响范围、责任人和复测。造成越权、证物账实错误或正式事实损坏的缺陷关闭并复测后方可上线；其他缺陷按批准的严重级别、期限及正式风险接受处理。验收必须保存场景、样本、规模、目标、实测和责任人，不得以演示截图代替测试证据。

## 13. 产品设计系统实施细则

### 13.1 设计资产与组件治理

设计系统是设计稿、代码和验收的共同依据。产品设计负责人维护页面模板、组件状态、文案与交互说明；前端负责人维护令牌、共享组件和使用示例；测试负责人维护验收用例。每项资产必须记录版本、负责人、变更日期、支持状态及适用范围。业务页面需要新样式时先检索现有令牌／组件，确有缺口再通过评审扩展，禁止复制一套外观相似但行为不同的控件。

每个共享组件交付时至少包含：用途、适用／不适用场景、属性与事件、尺寸、正常／悬停／焦点／禁用／加载／错误状态、键盘操作、屏幕阅读器语义、响应式表现、示例和自动化测试。业务状态由后端及领域模型定义；设计系统只提供状态的视觉承载，不自造业务状态或权限规则。组件不应在控制台打印输入值和敏感对象。

### 13.2 令牌、尺寸与布局基线

以下数值是统一设计的**建议默认值**，需要在目标屏幕、浏览器、中文字体和对比度评审后冻结；局部适配需记录原因。推荐用 CSS 自定义属性集中定义，组件消费语义令牌，不直接引用业务页面中的色值或像素常量。

| 类别 | 建议令牌及默认值 | 使用规则 |
|---|---|---|
| 间距 | `space-1/2/3/4/6/8` = `4/8/12/16/24/32px` | 控件内部、字段、卡片和区块按层级使用；不依赖空格字符排版 |
| 字体 | `text-xs/sm/base/lg/title` = `12/13/14/16/24px` | 中文正文默认 14 px，辅助信息不能小到无法辨识；允许用户缩放 |
| 行高 | 正文 `1.5`，标题 `1.3` | 长文本换行后不裁切；不得固定行高截断错误说明 |
| 圆角 | 控件 `6px`、卡片 `8px` | 全站统一；状态不靠圆角区分 |
| 边框 | `1px`、默认 `#D8E1EA` | 禁用、错误、聚焦和选中状态使用独立语义令牌 |
| 控件高度 | 常规 `36px`，紧凑 `32px`，强调或触控 `40px` | 同一表单默认同尺寸；点击区域以支持环境和无障碍评审为准 |
| 聚焦 | 至少 `2px` 可见轮廓及间隔 | 与相邻背景形成足够对比；不得用 `outline: none` 移除而无等效替代 |
| 层级 | 页面、下拉、固定头、抽屉、弹窗、通知采用集中管理的层级令牌 | 不在业务页随意递增 `z-index`；弹窗中的下拉不被遮挡 |

样式令牌要分别定义文字、图标、边框、背景的正常、悬停、激活、聚焦、禁用及错误组合。表格行选中与焦点需要同时可见；禁用样式不能模仿加载中状态。视觉评审应记录实际前景／背景及状态的测量结果，不能仅凭品牌色的理论对比度宣称整套界面合格。

### 13.3 页面模板和信息结构

| 模板 | 必备区域 | 关键行为和验收 |
|---|---|---|
| 工作台 | 标题、范围和更新时间、待办／已授权指标、快捷入口 | 指标可追溯口径；跳转重新授权；数据不可用时显示未知，不用零代替 |
| 列表 | 标题与操作、筛选、结果摘要、表格、分页 | 搜索／重置行为明确；首屏及每项空／错误状态完整；总数仅按授权返回 |
| 详情 | 返回路径、标题和状态、必要概览、分区信息、时间线、可用操作 | 清楚区分事实、来源、草稿及历史；版本冲突后刷新并提示；访问行为按要求审计 |
| 新建／编辑 | 页面标题、分组字段、必要说明、主次操作、错误汇总 | 字段顺序符合工作流；未保存离开需提示；失败保留输入；高风险提交复核 |
| 审批／核验 | 待办对象、申请依据、变更前后、附件／来源、意见、审批操作 | 同一人不得绕过职责分离；版本、授权及审批有效期在提交时重验 |
| 导入／批处理 | 来源与模板、文件检查、映射、预览、确认、进度及逐项结果 | 明确阶段和剩余动作；部分成功与冲突可追溯；完成后保留对账入口 |
| 任务／操作记录 | 任务标识、状态、发起时间、处理阶段、结果／失败原因、可用动作 | 刷新或断线后可查询；取消、重试和已生效结果的含义明确 |

筛选区默认显示最常用条件，其余条件可展开；“查询”应用当前条件，“重置”恢复默认条件并明确是否立即查询。不可直接把尚未提交的筛选作为已生效条件。用户保存的筛选、列配置及页面偏好不得包含敏感字段值或绕过当前权限，服务端和客户端缓存均应有失效策略。

### 13.4 组件状态及行为验收矩阵

| 组件 | 必测状态与交互 | 易遗漏的约束 |
|---|---|---|
| 按钮／链接 | 默认、悬停、键盘焦点、按下、禁用、加载、异常恢复 | 表单内非提交按钮显式指定类型；链接用于导航、按钮用于动作；禁用原因不能只靠鼠标悬停查看 |
| 输入／多行文本 | 空、预填、只读、禁用、必填、格式错误、最大长度、粘贴、输入法组合 | 不自动清除用户输入；长度按数据字典口径校验，服务端最终校验 |
| 下拉／搜索选择 | 加载、空、错误、选中、清除、失效选项、键盘上下选择与退出 | 可搜索请求需取消或丢弃过期响应；默认值必须有业务依据；不得把旧值静默换成首项 |
| 日期／时间／数字 | 边界值、空值、手动输入、时区／单位、非法格式、精度 | 起止顺序由后端验证；重量采用十进制字符串，不能通过浮点计算或隐式单位换算 |
| 表格 | 载入、无数据、无结果、失败、排序、分页、窄视口、选中与跨页 | 保持稳定行标识；列头可访问；批量动作逐项重新授权，不将不可见行默认为已选 |
| 弹窗／抽屉 | 打开、初始焦点、Tab 循环、Escape／取消、提交中、冲突、关闭后焦点 | 依据操作风险决定是否允许遮罩关闭；提交中避免误关闭，但必须提供可理解的恢复路径 |
| 状态标签／步骤条 | 已知状态、未知状态、历史、可用动作、长文案 | 文本和样式一致，未知状态不推导成成功；流程步骤不能代替真实审批与事件记录 |
| 上传／下载 | 格式和大小校验、进度、取消、检查中、失败、失效及受权下载 | 客户端校验仅作体验；服务器最终检查内容、权限及状态，未通过检查不能引用 |
| 提示／通知 | 短消息、持久警告、字段错误、异步状态、部分成功、撤权后的跳转 | 不只依赖自动消失；通知不包含未经授权的案情或敏感字段 |

表单提交校验失败时，在页面适当位置显示错误摘要并将焦点移至摘要或首个错误字段；字段用可访问关系关联错误说明。成功后明确结果与下一步；长时间处理显示任务进度，网络中断时保留输入并提供安全的结果查询路径。错误提示应说明事实及可行处理，例如“记录已更新，请刷新后重新核对”，不得直接展示数据库错误。

## 14. 工程结构、编码与契约细则

### 14.1 目录、边界和命名

当前 `frontend/` 与 `backend/` 目录可以继续使用；下列结构是按功能演进的**目标建议**，不是要求立即搬迁，也不意味着这些目录已经存在。新增代码应避免把所有业务继续堆入单个页面或路由文件；搬迁需保留启动、迁移和测试兼容性。

```text
frontend/src/
  app/              # 应用装配、路由与权限呈现
  shared/           # 设计令牌、通用组件、API 基础设施与工具
  features/         # 按案件、证物等业务域组织页面、类型与测试
backend/wellspring/
  api/              # 请求、响应、认证依赖和路由
  application/      # 用例编排、事务和授权调用
  domain/           # 状态、规则及领域对象
  infrastructure/   # 数据库、文件、任务及外部适配器
  modules/          # 按业务域组织的实现与契约
backend/migrations/ # Alembic 迁移
backend/tests/      # 单元、集成、权限和一致性测试
```

- 目录划分以清晰依赖关系为准，不以目录层数或抽象数量衡量质量。组件名、类型名使用 `PascalCase`；TypeScript 变量和函数使用 `camelCase`；Python 模块、变量、函数及数据库字段使用 `snake_case`；领域状态使用稳定的大写代码。名称表达业务含义，不把内部技术缩写暴露为用户文案。
- 明确 API 输入／输出模型和领域模型，迁移、接口及字典随改动提交。禁止静默吞掉异常、使用宽泛捕获掩盖失败、把密钥与环境差异编码在源码中。
- 依赖变更说明用途、许可证、版本及安全影响；新增 UI 组件、浏览器 API、后台服务或系统扩展需验证目标环境和离线制品。Python 直接依赖固定版本并不足以构成完整可复现锁文件，须锁定传递依赖、解释器及平台制品并核验摘要。
- 配置按环境提供可公开的示例和启动校验；缺失必需配置时明确失败，不回退到不安全的生产默认值。公开配置项应说明用途、类型、默认值、敏感级别、来源和重启／热更新方式。

### 14.2 API 响应、错误与兼容

建议在正式 API 契约中冻结以下结构；除分页结构外，成功响应不强制增加无意义的二次包装。接口可以按需求提供单对象、集合、`204 No Content` 或任务标识，但必须在 OpenAPI 与客户端测试中说明。示例为目标契约，当前开发接口尚未实现。

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请检查填写的信息",
  "request_id": "示例请求标识",
  "details": [{"field": "weight", "code": "PRECISION_EXCEEDED", "message": "重量最多支持六位小数"}]
}
```

| 错误代码示例 | 适用情况 | 客户端行为 |
|---|---|---|
| `UNAUTHENTICATED` | 未认证或会话无效 | 清理授权缓存，按批准方案重新认证；保留不敏感的未提交内容时需符合安全策略 |
| `FORBIDDEN`／`NOT_FOUND` | 未授权／不存在 | 按接口防泄露策略呈现通用信息，禁止客户端枚举对象 |
| `VALIDATION_ERROR` | 参数或字段无效 | 定位字段并保留输入；业务校验仍以服务端为准 |
| `VERSION_CONFLICT` | 数据版本已变化 | 提示重新获取并核对差异，不能自动覆盖后重试 |
| `STATE_CONFLICT` | 当前状态不允许操作 | 刷新授权内的对象状态并提示可用路径 |
| `IDEMPOTENCY_CONFLICT` | 同一幂等键对应不同请求 | 停止重复操作并提示核查原请求 |
| `RATE_LIMITED`／`SERVICE_UNAVAILABLE` | 限流或服务暂不可用 | 按响应约定延迟重试或查询结果，不对非幂等写操作盲目重放 |

错误码一经发布保持语义稳定；新增字段应采用可兼容扩展，删除字段、修改字段类型或改变语义属于破坏性变更，须走版本、消费者影响、迁移与下线流程。`request_id` 应由服务端或可信网关校验／生成，关联应用日志、任务和审计，但不得编码身份或敏感内容。接口清单应标明操作权限、数据范围、字段级规则、幂等性、超时、错误及审计要求。

### 14.3 乐观并发与幂等参考协议

1. 记录读接口返回明确的 `version` 或经批准的 ETag；写接口提交原版本（或使用 `If-Match`），服务端在**同一事务**内原子比较并更新。对象、审批依据或授权变化时拒绝旧请求，返回不泄密的冲突及可安全获取的后续处理信息。是否使用 HTTP 412 或业务 409 应在 API 契约统一冻结。
2. 对建档、分样、导入确认、执行处置等可能重复生效的命令要求幂等键。服务端按主体／授权范围、操作和键建立唯一约束，保存规范化请求摘要、执行状态和结果引用；权限范围及请求摘要的具体规范须设计并测试。并发请求同键只能有一个取得执行权。
3. 相同键和相同请求的已完成重试，在**重新授权**后返回原结果或可查询引用；相同键但内容不同返回 `IDEMPOTENCY_CONFLICT`。处理中请求返回明确的处理中状态及查询方式；若权限已撤销，不能凭旧键取回原敏感结果。
4. 幂等记录、正式业务变更和关键审计应处于同一事务或使用可恢复的协调机制；进程崩溃、事务回滚、响应丢失、过期清理及外部副作用必须有明确定义。幂等键保留期限不能短于获批的重试／对账窗口，过期不意味着可以对已发生业务重复记账。

### 14.4 数据、迁移和索引设计审查

每张核心表提交表用途、主键及唯一范围、数据责任人、敏感分级、数据来源、保留策略、访问／写权限、索引与增长预估。金额和质量使用定点类型，约束单位及范围；重量事件使用独立操作关联和原事件引用，余额与流水可对账。时间字段区分发生、录入和生效时间，数据库默认时间不能替代事实发生时间。

迁移评审必须覆盖：全新安装、旧版本升级、向前／向后兼容窗口、耗时与锁影响、失败后修复、备份恢复、数据校验和部署顺序。需要降级时先确认新旧应用及数据库兼容；不可逆数据变更以经过演练的恢复或前向修复为准，不承诺任意 `downgrade` 都无损。查询按授权范围建立索引并以代表性数据和执行计划验证，避免把个人标识或其他敏感值写入性能日志。


### 14.5 文件大小、分类存放与拆分规则

代码结构以业务边界和依赖方向为先，文件大小是可维护性门禁，不能靠把代码机械拆成大量无意义文件来规避。行数统计使用“有效代码行”：空行、纯注释和自动生成的格式化内容不计；评审工具应记录统计方法。

| 文件类型 | 建议目标 | 评审阈值 | 默认硬上限 |
|---|---:|---:|---:|
| Vue 单文件组件（模板、脚本、样式合计） | ≤ 250 有效行 | > 350 行必须说明拆分方案 | > 500 行禁止合并 |
| TypeScript／JavaScript 模块 | ≤ 250 有效行 | > 350 行必须拆分或说明 | > 500 行禁止合并 |
| Python 业务模块／路由模块 | ≤ 300 有效行 | > 400 行必须拆分或说明 | > 600 行禁止合并 |
| 测试文件 | ≤ 400 有效行 | > 600 行按场景拆分 | > 800 行禁止合并 |
| SQL／迁移文件 | 以单一迁移目的为准 | > 500 行需评估锁表和回滚 | 自动生成或数据迁移例外，必须单独评审 |
| 配置／字典文件 | 按领域或环境拆分 | > 300 行检查是否混合职责 | 禁止把密钥、业务规则和环境配置混在一起 |

以下情况必须拆分：文件同时包含多个业务域、页面同时承担列表／详情／编辑／审批、路由文件包含领域规则、组件直接编写数据库或权限逻辑、同一函数需要通过大量分支处理不同状态、或测试文件包含多个互不相关的流程。拆分优先按领域、用例或职责命名，不创建无法表达用途的 `common.ts`、`utils.py`、`misc.py` 大杂烩。

允许超过阈值的例外包括框架生成文件、锁文件、单次数据迁移、完整契约样例和确需同文件阅读的静态字典。例外必须在合并请求中写明原因、影响、后续拆分计划（如需要）和评审人；硬上限例外由技术负责人批准，不能用例外放宽安全、权限或审计门禁。

推荐按以下目录分类存放；实际目录可以因仓库组织调整，但同一业务域不得在多个无约定目录中重复实现：

```text
frontend/src/
  app/                 # 应用装配、路由、全局错误和权限呈现
  shared/ui/           # 按钮、表格、表单、弹窗、提示、设计令牌
  shared/api/          # HTTP 客户端、认证、错误和请求关联
  shared/types/        # 跨域稳定契约类型
  features/cases/      # 案件页面、组件、API、类型和测试
  features/evidence/   # 证物页面、组件、API、类型和测试
  features/<domain>/   # 其他业务域

backend/wellspring/
  api/                 # 路由、请求／响应模型、认证依赖
  application/         # 用例、事务、授权编排和命令
  domain/              # 实体、值对象、状态和领域规则
  infrastructure/      # 数据库、对象存储、任务和外部适配器
  modules/<domain>/    # 按业务域组织的完整实现
backend/tests/
  unit/                # 纯规则和计算
  integration/         # API、数据库、迁移和事务
  authorization/       # 角色、组织、字段和 RLS
  data_integrity/      # 流水、幂等、并发和恢复
  e2e/                 # 关键用户路径
```

同一功能的页面、API 客户端、类型、状态映射和测试优先共置于同一业务域；跨域共享代码只能放入 `shared` 或明确的基础设施层，并禁止反向依赖业务页面。`api` 层不得直接调用另一个业务域的数据库表；通过应用服务或公开契约协作。

### 14.6 文件、类、函数和测试命名

- Python 文件和模块使用 `snake_case`，例如 `case_service.py`、`evidence_repository.py`；类使用 `PascalCase`，函数、变量和数据库字段使用 `snake_case`。
- Vue 组件使用 `PascalCase.vue`，并以领域对象或用途命名，例如 `CaseList.vue`、`EvidenceWeightForm.vue`；页面组件使用 `Page` 或路由用途后缀，避免 `Component1.vue`、`Common.vue`。
- TypeScript 模块使用小写 `kebab-case` 或项目冻结的统一风格；建议 `case.api.ts`、`case.types.ts`、`use-case-list.ts`、`format-weight.ts`。同一仓库不得混用 `caseApi.ts`、`case_api.ts`、`case-api.ts` 三种风格。
- Composable 以 `use` 开头，Pinia／状态模块以领域名开头；API 客户端、领域服务、仓储和适配器在文件名中体现职责，不能只叫 `service` 或 `helper`。
- 测试文件与被测对象对应：Python 使用 `test_case_service.py`，TypeScript 使用 `case-list.spec.ts` 或项目统一后缀；测试名称说明场景和结果，例如 `rejects_cross_org_read`，不使用 `test_1`。
- 路由、接口模型、状态代码和数据库迁移使用稳定的英文标识；用户看到的中文名称由文案／字典层提供。变量、文件名和 URL 不使用拼音、中文、空格、表情符号或含义不明的缩写。
- 一个文件的默认导出、公共类或公共函数应与文件主名称对应；导出多个无关公共符号必须拆分。重命名需要同步更新导入、路由、测试、文档和追踪链接。

### 14.7 前端路由、后端路由与 URL 规范

**前端路由：**

1. 路径使用小写 ASCII 和连字符，按资源和页面语义命名，例如 `/cases`、`/cases/:caseId`、`/cases/:caseId/edit`、`/evidence`；不使用中文、空格、大小写混排或拼音缩写。
2. 路由 `name` 使用稳定的 PascalCase 或项目冻结的单一风格，例如 `CaseList`、`CaseDetail`、`CaseEdit`；路由名称全局唯一，不能用页面显示文案作为唯一标识。
3. 页面路径表达导航资源，动作由页面内按钮或明确的命令接口表达；不要使用 `/doCase`、`/handle`、`/getList` 等技术动作路径。详情路径只放不透明 ID，不把姓名、手机号、案情、搜索词或令牌放入 URL。
4. 页面状态通过受控查询参数表达，例如 `?page=1&page_size=20&sort=created_at&order=desc`；字段白名单、长度、数量和敏感内容由服务端校验。复杂表单、临时草稿和敏感条件不放入可复制、可记录或可分享的 URL。
5. 每个需要鉴权的路由配置页面元数据（所需权限、数据范围、标题和是否允许缓存）；路由守卫只改善体验，最终授权必须由服务端完成。未授权、过期和不存在按批准的防泄露策略处理。

**后端 API 路由：**

1. 正式接口使用统一版本前缀和小写复数资源名，建议 `/api/v1/cases`、`/api/v1/evidence-items`；资源层级优先不超过三层，只有确实表达授权和归属关系时才嵌套。
2. `GET` 用于读取，`POST` 用于创建或明确命令，`PUT` 用于完整替换，`PATCH` 用于部分更新，`DELETE` 仅用于经批准的可删除资源；关键业务事实优先使用状态／冲正／撤销命令而非物理删除。
3. 普通 CRUD 路径使用名词，不使用 `get`、`list`、`create`、`update`、`delete` 等重复 HTTP 语义的动词。确需表达领域命令时使用稳定动作名，例如 `POST /api/v1/cases/{case_id}/submit`、`POST /api/v1/evidence/{evidence_id}/sample`；命令必须有独立权限、幂等和审计。
4. 路径参数只使用不透明 ID；不能把可推断的身份证号、手机号、受案号或其他敏感标识作为路径参数。关系查询优先使用父资源和受控查询参数，不设计无限层级路径。
5. 查询参数统一使用 `snake_case`，例如 `page_size`、`created_from`；排序字段使用服务端白名单，过滤条件和分页在授权后执行。参数不得把 SQL 片段、任意字段名或内部表名直接交给数据库。
6. URL 只承载资源定位和非敏感、可审计的查询状态；禁止放密码、访问令牌、完整文书、人员敏感标识或未经批准的自由文本。URL 规范化、长度和编码由网关及应用共同限制，超限返回明确校验错误。
7. URL 保持简洁但不牺牲资源语义：删除重复前缀、技术实现名和无意义层级，避免把多个动作拼成一个路径。示例：使用 `/api/v1/cases/{case_id}/evidence`，不用 `/api/v1/getCaseEvidenceListByCaseId`。

**路由评审清单：** 新路由必须说明资源／命令、HTTP 方法、权限、数据范围、敏感字段、幂等性、版本、错误码、审计事件和兼容／废弃计划；路由命名通过后再编写前端调用，禁止先在页面里拼接临时 URL。

### 14.8 注释、文案与日志语言

- 用户可见的按钮、标签、占位符、空状态、加载状态、成功、失败、确认、权限和错误提示使用中文；技术名词可在中文语境中保留英文原名。
- 新增代码注释使用中文，只解释复杂逻辑、边界条件、数据不变量和非显然决策；不为简单赋值写注释，也不保留无效注释。
- 业务日志使用中文描述操作结果、任务状态和安全事件摘要；结构化字段、错误码、协议名称和第三方 API 名称可以使用稳定英文标识。日志不得记录密码、令牌、完整敏感字段、原文和模型输入。
- 控制台调试输出、TODO、FIXME 和临时提示不得遗留在交付代码中；确需保留的技术说明使用中文并关联工作项。
- 错误文案应说明事实、影响和下一步；不要把 `Error`、`Failed`、`Loading...` 等英文内部状态直接展示给用户。
- 所有源文件、文档和用户数据样本使用 UTF-8；提交前检查乱码、不可见控制字符和错误换行。

## 15. 研发门禁、风险分级与证据管理

### 15.1 风险分级和验证深度

| 级别 | 典型变更 | 最低审查与验证 |
|---|---|---|
| 高 | 认证、授权、RLS、审计、导出、证物计量、审批、迁移、保留与恢复 | 领域＋安全／数据责任人参与；正反向权限、并发、事务回滚、审计、恢复及相关端到端证据 |
| 中 | 一般业务状态、查询、导入预览、外部依赖及任务 | 领域与同行评审；契约、异常、权限及受影响集成测试 |
| 低 | 无业务含义的文案、样式及局部非敏感展示 | 受影响页面的视觉、键盘与回归检查；若改变权限表达或隐藏信息则提升风险级别 |

风险等级由变更影响确定，不由文件类型或代码行数确定。评审记录必须包含变更范围、风险、测试结果、残余问题及责任人；对高风险变更，审查人应与作者分离且有相关领域能力。

### 15.2 门禁执行与失败处置

| 环节 | 机器可检查的条件 | 人工判定／证据 | 未通过处理 |
|---|---|---|---|
| 提交／合并请求 | 依赖安装、格式／静态检查、类型、单元、构建、秘密扫描 | 范围及设计符合规范，关键业务评审 | 禁止合并；修复并对最新提交重跑 |
| 集成验证 | API／数据库集成、迁移、授权、RLS、并发及契约检查 | 测试环境、非特权角色和样本符合场景 | 阻断进入候选发布；保留失败报告 |
| 候选发布 | 制品摘要、SBOM、许可证、漏洞门禁、端到端及安全检查 | 缺陷分级、风险接受、兼容及升级方案 | 缺少证据或阻断问题未关闭，不得发布 |
| 生产发布 | 版本、配置、迁移与备份检查；健康和关键指标核验 | 授权审批、恢复演练、运维交接和回退决定 | 停止或依批准预案回退／前向修复并记录 |

CI 必须与分支保护绑定，任务不执行、跳过、超时或无报告不得显示为通过。门禁必须对最终待合并提交及实际交付制品有效，制品一经验证不得重新构建替换而沿用原报告。扫描误报或暂不修复必须记录影响分析、补偿措施、责任人与有效期，并由有权责任人批准；例外不得覆盖法律审批或本文明确的上线阻断条件。

自动检查的执行命令、工具版本、覆盖范围、报告路径及失败退出码，随着 CI 实际落地维护在工程文档中。正式门禁不能以人工勾选代替可自动验证的步骤，也不能以扫描和覆盖率数字代替对业务规则的评审。

### 15.3 自动化规范检查

项目应提供可在干净环境运行的规范检查入口，并纳入 CI 和合并门禁。检查至少覆盖：

- 文件编码、乱码、禁止提交的密钥／令牌／真实敏感数据和调试输出。
- 文件大小阈值、目录边界、命名风格、未使用导出和循环依赖（工具可用时）。
- API 路由版本、资源命名、HTTP 方法、分页参数白名单和 OpenAPI 契约差异。
- 前端是否直接访问数据库／对象存储管理口、是否出现不受控内联样式、硬编码主题色和未登记 URL。
- 迁移模型差异、依赖锁文件、SBOM、许可证和漏洞扫描。

当前仓库已有后端测试、Alembic 检查和前端构建，但尚未形成完整的规范检查脚本。未配置的检查应标记为“待建设”，不能在人工清单中勾选为已通过。自动检查误报必须通过规则修正或显式、可追踪的豁免处理，禁止直接绕过门禁。

### 15.4 缺陷分级及问题闭环

| 级别 | 判定示例 | 发布处理 |
|---|---|---|
| 阻断 | 未授权访问成功、账实或正式事实损坏、关键审计丢失、无法恢复、关键流程不可完成 | 停止上线，修复、复测并记录证据 |
| 高 | 重要业务功能大范围不可用、敏感数据保护不足或关键数据错误 | 原则上关闭并复测；其他处理须按适用制度由有权负责人书面决定，不能覆盖阻断条件 |
| 中 | 局部流程受影响且存在可行替代路径 | 记录影响、临时措施、负责人和整改期限，按批准标准决定 |
| 低 | 不影响业务判断的文案、布局或低频体验问题 | 纳入计划，避免长期积压 |

缺陷级别、响应时限和风险接受权限由建设单位冻结；上表是判定基线，不预设未经批准的 SLA。回归测试应覆盖修复本身及相邻权限、数据和流程，不因问题无法复现就直接关闭。

### 15.5 可追溯证据与完成定义

每个功能应能沿“需求 → 原型 → 接口／字段／状态 → 代码变更 → 测试用例与报告 → 发布制品 → 验收结论”双向追溯；每一步有唯一标识、版本、负责人和链接。测试与评审材料不得带入未授权真实数据，证据须有访问权限及保留策略。

完成的定义包括：批准范围内的正常和异常路径已实现；服务端权限、审计、状态和数据约束已验证；界面反馈和无障碍检查完成；自动与人工门禁通过；文档、运维、迁移及发布信息已更新；遗留问题按规定处理。仅“代码已提交”“页面可以打开”或“演示成功”均不能认定为完成。

## 16. 安全工程与运维处置细则

### 16.1 威胁建模与常见攻击面

涉及认证、敏感检索、上传／导出、审批、跨组织、AI 或新外部依赖的设计须识别资产、信任边界、入口、威胁、控制、测试和责任人。至少评估：越权访问及对象枚举、会话盗用与重放、XSS／CSRF（适用 Cookie 时）、注入、恶意文件、资源耗尽、敏感数据外泄、任务越权及提示注入。测试和防护以批准的安全架构为准，不将通用清单视为合规认证。

认证方案须明确 Cookie 或令牌的实际采用方式及撤销机制。若采用 Cookie，配置 `HttpOnly`、`Secure`、`SameSite` 并实施与部署匹配的 CSRF 防护；若采用令牌，规定保存、传输、有效期、服务端撤销与泄露处置。禁止在 URL、访问日志、错误报告或浏览器长期存储中放置长期凭据。跨域策略应基于受信来源白名单，不以开放全部来源作为生产默认。

上传与解析除了文件扩展名，还须按批准策略检查实际类型、文件大小、压缩深度、宏／恶意内容和解析 CPU／内存／时间；解析失败文件进入隔离或受控清理。导出 CSV／表格时评估公式注入，针对用户可控单元格采用经批准的安全编码策略并验证不破坏业务数据。文件名、响应头、路径和对象键不得信任用户输入。

### 16.2 运行指标、告警和事件处置

| 监控对象 | 最低观测内容 | 处置方向 |
|---|---|---|
| API | 可用性、请求量、错误率、P95／P99、限流、认证异常 | 定位受影响范围，检查依赖、发布与资源；不得记录敏感请求体 |
| PostgreSQL | 连接、锁等待、事务错误、磁盘、复制／备份状态 | 检查容量与长事务，依批准流程处理，不能临时赋予运行账号超级权限 |
| Worker／任务 | 待处理数量、最老等待时间、租约、重试与失败 | 核验代次、授权及幂等状态后重放；不得直接修改正式结果 |
| 文件与审计 | 对象缺失／摘要异常、归集积压、投递失败 | 停止引用或敏感操作，执行补偿、对账与告警升级 |
| 安全和容量 | 异常访问、账号变更、资源用量及证书有效期 | 按责任人和分级处置，记录时间线和恢复验证 |

每个生产告警需指定负责人、触发和恢复条件、抑制／升级规则、影响说明与操作手册。性能目标、容量、重试次数、日志保留和告警阈值必须结合实际负载及主管要求冻结；开发人员不得把示例值当作已批准运行目标。

事件处置按“发现与定级 → 限制影响 → 保全证据 → 定位与恢复 → 核对业务／审计 → 复盘整改”执行；记录操作主体、时间、依据和影响，严禁为恢复速度直接抹去流水或跳过授权。演练要覆盖数据库及对象存储共同恢复、任务重复处理、权限撤回和审计归集故障，记录实测恢复点及结果。

## 19. 产品文案、术语与数据呈现规则

### 19.1 文案风格

- 面向用户的文案使用简体中文、短句和明确动词；同一概念只使用一个中文名称。产品名、功能名、状态名、按钮名、字段名和接口状态码建立术语表，不由页面作者临时翻译。
- 文案说明“发生了什么、影响是什么、用户下一步做什么”，不责备用户，不把内部异常转嫁给用户。禁止使用“系统错误”“操作失败，请重试”作为唯一说明；在不泄露内部细节的前提下给出可执行路径。
- 重要数据使用完整单位和时间语义，例如“重量（克）”“提交时间（北京时间）”；空值使用统一的“未填写”“未核验”“不适用”或经业务确认的词，不用空白、`-` 和 `0` 混淆不同含义。
- 状态文案、提示文案、错误码和帮助说明经过产品与业务评审；高风险操作的说明必须与审批制度一致。生产日志、审计事件和用户文案可以使用不同粒度，不能为了日志方便把内部字段直接展示给用户。

### 19.2 状态与枚举治理

每个枚举至少维护稳定代码、中文名称、定义、是否终态、允许动作、来源、版本、生效／失效时间及兼容策略。代码一经用于正式数据不能复用表示另一含义；停用值仍能被历史数据安全展示。未知值必须可观测并安全降级，不能因为前端未更新而默认为“已完成”。

### 19.3 脱敏、复制与导出

脱敏规则按字段和场景维护，例如列表、详情、搜索摘要、日志、通知、导出和错误信息分别评审。复制按钮、浏览器剪贴板、打印、下载、截图提示和批量导出都属于数据流出点，必须使用当前授权和审计规则。前端遮盖不等于数据保护；接口响应、缓存、预加载和对象存储元数据同样不得返回无权字段。

## 20. 性能、兼容性与可观测性预算

### 20.1 指标定义和冻结

性能目标必须同时记录测试环境、数据量、并发模型、查询组合、缓存状态、客户端网络、统计分位数和错误率。下表为用于设计和压测的建议起始预算，阶段 0 应根据目标环境批准后替换；没有实测和批准，不得在对外材料中声称已达到这些数值。

| 场景 | 建议起始预算 | 必须观察 |
|---|---:|---|
| 登录、健康检查等轻量请求 | P95 ≤ 500 ms | 错误率、数据库连接和认证限流 |
| 授权后的普通列表首屏 | P95 ≤ 1.5 s | 数据量、分页、授权过滤和查询计划 |
| 详情及时间线 | P95 ≤ 2 s | 关联查询、附件元数据和敏感字段过滤 |
| 提交短事务命令 | P95 ≤ 2 s | 锁等待、冲突、幂等命中和事务回滚 |
| 异步任务创建 | P95 ≤ 500 ms | 入队成功率、最老等待和最终失败 |
| 前端初始静态资源 | 目标环境下记录 LCP、脚本大小和缓存命中 | 不得以公网 CDN 可用作为内网部署前提 |

所有预算必须有负载规模和接受人；P95 不是唯一上线标准，越权、错误、数据一致性和恢复能力优先于单纯延迟。接口超时、数据库查询超时、Worker 资源上限和上传解析限制分别配置，避免用一个全局超时掩盖风险。

### 20.2 浏览器、分辨率和离线兼容

目标浏览器、版本、操作系统、输入法、打印／扫描设备和辅助技术形成支持矩阵。每次前端依赖或浏览器升级做冒烟、关键流程、下载／打印、键盘和缩放回归；不支持的浏览器在登录前或部署说明中明确。离线环境的字体、图标、静态资源、模型和依赖从受控制品提供，不运行时访问公网。

### 20.3 关联标识和可观测性

请求、任务、审计和外部调用使用可关联的随机 ID；ID 不编码身份、组织、时间或敏感业务值。日志按级别和采样策略记录开始、结束、结果、耗时、依赖和错误代码，默认不记录请求体、完整查询词、令牌、原文及敏感字段。需要排障的敏感信息使用经批准的摘要或受控引用，并设置访问和保留策略。

指标按服务、路由、结果类别和依赖维度聚合，避免将案件编号、人员标识、原文或用户输入作为高基数标签。分布式追踪、日志和审计互相引用但职责不同：监控帮助排障，审计证明业务访问和变化；不能用普通应用日志代替受保护审计。
