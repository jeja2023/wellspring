# 10 角色与权限设计草案

> 状态：三级角色是已确认的设计方向；具体权限边界仍需确定。本文是设计方案，除明确标注的基础功能外尚未实现，仅可使用虚构数据验证。

2026-11-11 实现更新：已增加用户/角色/权限/组织管理、普通管理员本组织普通账号委派、模块操作权限及会话撤销，详见[系统管理与权限](../系统管理与权限.md)。下文保留设计方向与历史差距；未实现的跨组织、字段和专案授权不能因管理页面已增加而视为完成。

## 1. 角色结构

用户已确定保留组织：账号归属单位，组织作为业务数据范围的基础；角色区分普通用户、管理员和系统管理员。跨单位或特定案件的访问通过后续授权设计处理。组织层级、跨组织授权方式及字段范围尚待确认，现有组织过滤只是基础实现。

| 角色 | 职责和权限方向 |
|---|---|
| 超级管理员 | 拥有系统内全部功能和数据权限，包括账号、普通管理员、角色、业务、数据、导入导出及审计查看。现有 `admin` 作为初始超级管理员。 |
| 普通管理员 | 负责日常账号、组织、业务数据等管理，在超级管理员设定的权限和数据范围内操作。 |
| 普通用户 | 使用获授权的业务功能，在指定的数据范围和字段范围内工作，不具备系统管理功能。 |

这是系统应用权限，不能等同于数据库超级用户或操作系统管理员。超级管理员可以访问全部业务数据及敏感字段，也可以直接使用全部应用功能；系统仍需记录其操作。普通管理员和普通用户只获得明确授权的功能及数据范围。

## 3. 授权规则

- 每个账号的角色在服务端持久保存，接口根据当前有效账号、角色、操作权限、数据范围和字段范围检查；不得信任前端提交的角色或权限结论。
- 超级管理员具有全部应用权限和全系统数据范围，但账号停用或会话失效时不能继续访问。普通角色默认拒绝未授权操作；不同角色组合、组织和案件授权规则待确定。
- 普通管理员和普通用户的数据范围、字段权限适用于列表、详情、搜索、统计、Excel 导入导出和后台任务。服务端过滤和遮盖，不能仅隐藏页面按钮。
- 账号、角色、授权、数据修改、删除／恢复、导入导出及超级管理员操作应记录审计。审计信息不记录密码、令牌和完整敏感业务内容；审计存储保护与查阅方式待设计。
- 记录删除按用户已确认的方向保留并从普通列表隐藏；接警编号全系统唯一，已隐藏编号也不可重新使用。恢复权限、审批方式和数据保留时限待确认。

## 4. 初始账号与生命周期

- 本机 SQLite 开发库中的 `admin` 已标记为初始管理员。当前开发密码仅用于本机虚构数据测试；正式环境应单独初始化强密码，不能在镜像、源码或启动脚本中写入默认密码。
- 已确定设置独立的“系统运维”组织，供初始系统管理员归属。迁移 `0016` 将已有 `admin` 调整至该组织，历史业务数据仍属于原组织；目前除案件信息外的部分业务仍按组织过滤，需要后续补齐系统管理员全范围访问。
- Docker PostgreSQL 数据库独立于本机 SQLite，账号不会自动复制；首次初始化时由操作人员创建初始管理员。
- 管理员和普通用户由受授权账号创建、停用或调整权限；停用及权限撤销后应在约定时限内生效。防止误锁定最后一个超级管理员的处理方式待确定。
- 后续新增功能应纳入权限清单；超级管理员按设计拥有全部应用功能，普通角色只在明确授权后使用。

## 5. 当前实现和缺口

已实现用户、角色、权限与组织页面及模块操作授权；超级管理员配置系统，获授权普通管理员仅管理本组织普通账号。密码重置、用户/角色变更撤销旧会话，防并发锁定最后超级管理员。接警台账保留原有超级管理员跨组织查看，其他业务数据范围未因角色新增而扩大。字段/专案权限、跨组织共享、全部业务全范围访问、外部受保护审计及正式生产岗位验收仍未实现。

## 6. 实施顺序和验收

1. 明确普通管理员可管理的账号和组织范围，以及普通用户默认可使用的业务操作。
2. 建立角色、操作权限、账号角色与数据范围模型，设计已有账号的迁移；保证初始 `admin` 明确关联超级管理员角色。
3. 增加账号和权限管理页面及服务端接口，对普通管理员禁止越权授予和提升角色。
4. 将案件信息的查询、统计、详情、修改、隐藏／恢复和导入导出接入统一授权与审计；同时校验字段权限和范围。
5. 验证超级管理员全功能访问，普通管理员越权失败，普通用户系统管理访问失败，未登录和停用账号拒绝访问；覆盖列表、统计、导入导出、直接调用 API、角色变更、审计和并发场景。
6. 在目标 PostgreSQL 和 Docker 环境验证迁移、权限生效、备份恢复及账号初始化，经过验收后再评估真实数据使用。
