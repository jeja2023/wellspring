# 04 开发权限模型

> 这是个人开发阶段的最小权限假设，不是生产权限矩阵。

## 当前模型

| 主体 | 当前可做 | 当前限制 |
|---|---|---|
| 开发账号 | 按角色查询和办理本组织案件、接警、线索及分析建模资料 | 仅虚构数据；没有正式岗位矩阵、完整跨模块字段/专案授权和正式审批；人员、场所事件及污水等已有独立核验约束 |
| 初始管理员 `admin` | 维护账号、组织、角色、操作权限、系统日志和模型服务配置 | 超级管理员不自动获得其他组织业务资料；正式字段/专案权限仍待确认 |
| 未登录 | 健康检查 | 不能访问业务接口 |
| 已禁用账号／过期会话 | 无业务访问 | 服务端拒绝 |
| 其他组织账号 | 只能看到自己的组织 | 当前为组织过滤，不等于生产 RLS |

## 开发阶段硬规则

- 所有业务接口必须依赖服务端当前用户，不信任客户端提交的 `org_id`、角色和权限结论。
- 跨组织对象即使 ID 已知也应按“记录不存在或无权访问”处理，避免对象枚举。
- 新增敏感字段默认不返回，除非明确写入数据字典和展示权限。
- 开发数据不能导出到项目外部，也不能通过日志、异常、截图和 URL 泄露。
- 高风险功能先在虚构数据上验证状态、权限和审计，再考虑接入真实系统。

## 生产前待建模型

认证来源、角色、组织／辖区、案件／专案授权、字段遮盖、附件权限、临时授权、撤权窗口、紧急访问、运维与业务分离、RLS 和独立审计归集均待业务／安全确认。

具体候选角色、权限矩阵和实现顺序见 [角色与权限设计草案](10-角色权限设计草案.md)。

`0.0.6` 的 `0026` 彻底移除证物业务和 `evidence.*` 权限。数据建模、模型管理、技战法库合并到“分析建模”入口，页内标签继续分别校验原有 read/write 权限，不因合并导航扩大授权。


`0.0.6` 新增人员完整身份/敏感资料/核验/具体业务/交接权限及 `places.read/write/review`、`geography.read/write`。默认兼容角色只按 `0022`/`0024`/`0025` 补入大屏/AI 查询、线索流转和分析建模能力，`0026` 清理证物授权，不自动授予模型生成、人员敏感资料、场所或地图权限；已有自定义角色不自动扩权。地图读写须同时通过原模块权限，人员移交和线索下发只扩大明确授权对象的范围，不能据组织层级读取全部历史。完整矩阵见[系统管理与权限](../系统管理与权限.md)及[0.0.6 版本说明](../0.0.6-版本说明.md)。
