> 状态：基础线索与工单已作开发验证实现；其余内容为规划草案，只适用于虚构数据。业务规则、访问权限、数据来源和生产范围须确认。

## 一、“情”在现有方案中的位置

总体方案以“人、案、物、情”为目标，但没有定义独立、完整的情报业务闭环。现有内容主要分布在：

| 方案已有内容 | 位置 | 当前工程状态 |
|---|---|---|
| 线索草稿、人工核验和核查工单 | 2.1.2 | 开发验证切片已实现；正式岗位权限、时限及跨区协作未实现 |
| 跨区精确特征碰撞与协调 | 2.1.3、5.6 | 未实现 |

| `clue`、`clue_feature`、`collision_event`、`investigation_task` | 4.2 | 已建线索、工单及事件；特征与碰撞未建模 |
| 线索工单及碰撞纳入阶段 2；授权检索纳入阶段 3 | 9.2 | 未完成 |

“情报管理”中的登记、分类、来源评估、研判记录与成果管理在方案中尚未形成完整定义。本草案将其作为**新增建议**，是否纳入首期、如何办理及验收应另行确定；不能把这里的建议自动视为既定生产制度。

## 二、建议范围与边界

### 基于现有方案的首期能力

1. **线索管理：** 受控登记和查看线索草稿，记录来源、来源时间、录入者、核验状态、版本和访问范围；保留原始信息和变更。
2. **线索核查工单：** 授权核验后发起，分派承办单位、核查目标和期限；记录办理、退回、复核和关闭；逾期仅提醒，不自动确认事实。
3. **关联人、案、物：** 以带来源、时间、创建者、权限和核验状态的关系记录关联；未经核验不得自动建立正式人员／案件关联，不能因关联扩大任何一方的访问权。
4. **精确碰撞与协调：** 以获准特征和规则进行受控精确匹配；申请方仅获得经批准的最小必要反馈，协调岗位按专项授权处理。并发、防重、误报、续期与释放保留审计。
5. **授权检索：** 先按服务端权限限定范围，再召回、排序和复核；记录来源，中文检索效果需单独验证。

### 建议扩展（需确认范围与验收）

- 情报资料登记：区别线索、原始材料与人工研判；保留来源和采集方式，不把采集内容默认认定为事实。
- 分类与可信度评价：由授权人员依据业务批准的分类和评价标准记录；不将模型自报置信度等同于事实可信度。
- 研判记录与成果：保存依据、分析过程、结论、作者、复核、版本及引用范围；正式成果需按确定的审批权限发布。
- 待办、分发与反馈：按职责和数据范围分派；通知、附件、导出与访问审计跟随授权。

地图、关系图谱、语义检索和自动推断仍属于方案中的选做范围，不因增加“情报线索”入口自动纳入首期。未经批准，不接入外网抓取、跨网交换、外部模型服务或未经授权的数据源。

## 三、建议业务链路

`受控来源／人工录入 → 待核验草稿 → 人工核验 → 核查工单 → 办理与复核 → 已关闭或退回`

研判和跨区碰撞是经授权的协作能力，可在适当环节发起；线索核查结果与正式案件、人员或证物事实之间必须保留依据和独立审批。流程仅为草案，不预设办理期限或法定状态。

## 四、数据与关联设计草案

| 对象 | 建议保存的最小信息 | 注意事项 |
|---|---|---|
| 线索 `clue` | 不透明 ID、来源、摘要、组织范围、核验状态、创建者、时间、版本 | 人工录入、原文陈述和推断分开；摘要按字段权限输出 |
| 核查工单 `investigation_task` | 线索 ID、核查目标、承办方、截止时间、状态、版本 | 分派、办理、退回、复核、关闭使用追加事件；具体状态及权限待确认 |
| 受控特征 `clue_feature` | 特征类型、来源、有效期、受控匹配索引 | 敏感标识不放日志或 URL；是否采用 HMAC、密钥轮换和规范化规则待安全设计 |
| 碰撞及协调 `collision_event` | 不透明事件 ID、处置状态、受权协调记录 | 各方可见内容分离；查询次数、总数、错误与响应差异须测泄露 |
| 关联记录（建议） | 对象类型和 ID、关联类型、来源依据、创建者、时间、核验状态 | 只展示双侧均经授权且必要的字段；可见线索不意味着可见全部人员历史 |
| 研判记录（建议扩展） | 分析依据、结论、版本、作者、复核状态 | 与原始线索和正式事实分离，不由 AI 直接发布 |

字段、关系、审批与保留策略尚未冻结，不能直接作为数据库迁移或生产权限依据。

## 五、权限、安全与审计

- 线索、工单、特征、碰撞结果、附件和研判成果分别校验功能、组织／辖区、专案、字段及有效期；账号禁用、撤权和到期优先拒绝。
- 导航隐藏不能替代服务端授权；详情、列表、统计、搜索摘要、历史版本、附件、导出和任务结果遵循同等边界。
- 人员、案件、证物的权限单独复核，禁止通过情报关联扩大其他业务对象的可见范围。
- 记录查看、检索、分派、复核、关联、碰撞、释放和导出等关键审计；审计不复制完整敏感原文。关键变更和本地审计同事务提交。
- 保留来源与历史变更；合法期限、到期清理、冻结、误报处理和销毁应由数据责任人确认，不能自行硬编码。
- AI 仅输出可追溯候选和依据，人工逐项核验；未经确认不能写入正式事实或自动建立关系。

## 六、实施与验收顺序

1. **设计基线：** 先确定线索来源、对象关系、角色范围、工单状态、异常、数据字典和测试场景；使用虚构数据。
2. **基础线索与工单：** 在现有账号／组织验证边界上建立草稿与事件模型、列表及详情、核验／分派／办理／复核；开发环境不得宣称达到生产授权要求。
3. **人、案、物关联：** 先具备相关主档案及双侧授权，再实现有来源、可撤销、可审计的关联；未实现模块不做假链接。
4. **精确碰撞：** 在字段、密钥、最小反馈和专项权限经设计确认后实现，重点测试并发、重放、误报和信息侧漏。
5. **授权检索与研判：** 授权过滤进入查询边界；扩展功能经范围确认后实施，并以中文样本和权限反向用例验收。

最小验收至少覆盖：同组织授权／未授权、跨组织猜测 ID、字段及附件访问、关联对象两侧权限、重复提交和并发、退回及重分派历史、碰撞最小反馈及侧漏、撤权后检索与下载、AI 候选不能直接写正式事实。真实业务上线另需按批准矩阵及目标环境验证。

## 八、当前开发实现与限制

- `clues` 保留标题、来源、摘要、组织、创建者、状态和版本；状态为 `DRAFT → REVIEWED`，核验仅为虚构数据开发流程，允许同一组织用户操作。
- `investigation_tasks` 当前每条线索最多一个工单，承办人为本组织启用账号。`OPEN/RETURNED → PENDING_REVIEW → CLOSED/RETURNED`；提交人不得复核本人结果，结果变更保留在事件中。此流程是技术验证假设，不是已批准的业务制度。
- `intelligence_events` 追加记录参与者、前后状态、意见和提交结果；相关写入、幂等记录及本地审计同事务提交。离线迁移撤销运行账号对事件表的更新和删除权限，数据库权限未在目标 PostgreSQL 验证。
- 支持可选的手动办理期限和个人未关闭工单列表，不自动生成提醒或改变状态。暂不支持期限变更、跨区流转、附件、正式岗位授权、RLS、工单专项审批、人员／证物关联、精确碰撞与授权全文检索。账号列表最多显示 100 个本组织启用账号；只适合小规模开发验证。
- 开发环境按组织过滤，组织内一般账号均可核验或复核他人任务；未满足专案、角色、字段级权限或安全验收，禁止接入真实数据。

## 九、线索与案件关联开发切片（未发布）

- 已核验线索可以关联同组织可见案件，记录依据、操作者及时间；同一线索与案件同时只能有一个有效关联，数据库以部分唯一索引防重。
- 撤销须填写原因，原关联变为 `REVOKED` 并保留历史；可以重新创建新的关联，撤销不改变原案件或线索状态。
- 读取、创建、重放及撤销均复核线索和案件两侧的当前组织范围；写入携带幂等键与版本检查，事件、审计和业务更新同事务提交。
- `intelligence_events.related_link_id` 为可空关联标识（应用维护，当前没有外键）；已有事件迁移后为空。
- 尚无正式角色、跨专案、字段授权或 RLS，此功能仅供虚构数据验证。生产 PostgreSQL 并发与权限尚未验证。

## 十、核查工单重分派（未发布）

- 本组织开发账号可将 `OPEN`（待办理）或 `RETURNED`（已退回）的工单改派给本组织其他启用账号；待复核和已关闭的工单不得改派。
- 修改需填写原因并提交工单版本和幂等键；旧承办人的工作台不再显示该工单，只有新承办人可以提交核查。原提交结果和退回历史保留。
- 事件保存操作人、原因、修改前／后的承办人标识和状态；创建工单的新事件也记录初始承办人。`0006` 升级前的历史事件这两个字段为空，不追填或推断历史人员。
- 重分派、事件、审计及幂等记录同事务提交。当前仅按组织过滤，组织内一般用户均可发起；实际分派权限和跨区协作规则待确认。

## 十一、线索列表筛选（未发布）

已支持当前组织范围内按标题／来源的字面包含匹配及核验状态组合筛选；关键词位于 POST 请求体，不存入 URL 或本地审计，摘要不参与匹配。查询结果按创建时间及 ID 稳定排序，支持服务端分页。此实现不是中文全文检索，也不能代替正式角色、专案和字段授权；生产代理及应用监控不得记录查询请求体。
