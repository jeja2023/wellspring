# 03 接口契约草案

> 当前实现是开发接口 `/api`；正式接口目标为 `/api/v1`。本文件描述当前行为和迁移方向，不能替代最终 OpenAPI。

## 通用约定

- 认证：当前使用 `Authorization: Bearer <token>`；生产方式待确认。
- 内容类型：JSON 请求使用 `application/json`。
- 当前错误：统一使用 `code`、`message`、`details` 和 `request_id`。
- 当前列表：案件、证物和重量流水已支持授权范围内服务端分页及稳定排序，默认 20 条、最大 100 条。
- ID：使用不透明 UUID；不在 URL 放姓名、手机号、案情、令牌或完整文书。

## 目标示例

```http
GET /api/v1/cases?page=1&page_size=20&sort=created_at&order=desc
Authorization: Bearer <token>
```

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "has_more": false,
  "total": 0,
  "request_id": "example-request-id"
}
```

```json
{
  "code": "VERSION_CONFLICT",
  "message": "记录已被更新，请重新核对后再提交",
  "details": [],
  "request_id": "example-request-id"

```

## 路由评审规则

新路由必须说明资源／命令、HTTP 方法、权限、数据范围、幂等性、错误码、审计和兼容策略。普通 CRUD 使用名词和 HTTP 方法；领域命令才使用明确动作名，例如 `/submit`、`/sample`。不使用 `/getList`、`/doCase` 等技术实现型路径。

## 情报线索开发接口（0.0.2 开发验证）

所有接口使用现有服务端认证和组织范围；写请求要求 `Idempotency-Key`，不构成正式角色或字段权限。

| 方法 | 路径 | 开发验证行为 |
|---|---|---|
| GET | `/api/intelligence/assignees` | 返回本组织启用的前 100 个用户 |
| GET | `/api/intelligence/tasks/mine` | 获取当前组织、当前账号承办且未关闭的工单，按办理期限排序 |
| GET | `/api/intelligence/clues` | 按组织分页列出线索 |
| POST | `/api/intelligence/clues` | 创建线索草稿，包含标题、来源和摘要 |
| GET | `/api/intelligence/clues/{id}/detail` | 查询线索、工单和分页处理事件 |
| POST | `/api/intelligence/clues/{id}/review` | 按版本记录人工核验及说明 |
| POST | `/api/intelligence/clues/{id}/tasks` | 对已核验线索创建一个核查工单，指定同组织承办人，可填写 `due_date`（YYYY-MM-DD） |
| POST | `/api/intelligence/tasks/{id}/transition` | 按版本提交、退回或关闭工单；提交人与复核人分离 |

任务动作 `SUBMIT` 需提供核查结果；`RETURN` 和 `CLOSE` 需由非提交人执行，均需处理说明。完整状态及限制见 [情报线索范围草案](09-情报与线索范围草案.md)。
