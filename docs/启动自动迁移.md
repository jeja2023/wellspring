**本地启动自动迁移**

`python start.py` 在启动前后端之前运行受控迁移。它使用与 `migrate.py` 相同的 `.env`/`DATABASE_URL` 配置，并显示脱敏目标；判断依据为数据库 `alembic_version` 与程序中的 Alembic 迁移链，不依赖文件修改日期，也不会根据 ORM 自动改表。

手动入口固定为 `python migrate.py`，不随开发、测试、生产阶段再次改名。源码环境当前仍使用本机虚拟环境与本地配置；显式 `DATABASE_URL` 优先。离线容器使用 `docker compose ... run --rm migrate`，通过部署密钥和迁移账号选择环境。文件名不决定环境或数据库权限。旧 `migrate_dev.py` 仅保留转发兼容及更名提示，不维护第二套实现。

| 数据库状态 | 启动行为 |
| --- | --- |
| 已在当前 head | 不改表、不重复备份，继续启动 |
| 全新空数据库 | 执行当前可信程序的完整迁移链；不会自动创建账号 |
| 已有库，全部待执行迁移明确标记 `startup_safe = True` | 取得迁移锁、完成备份，再升级；版本复核成功后才启动 |
| 含未标记、标记 False 的迁移 | 停止，提示停服检查后执行 `python migrate.py` |
| 数据库版本领先/未知、迁移缺失、多个 head、已有表但无版本 | 停止；不自动降级、stamp 或合并分支 |
| 备份、加锁、升级或升级后版本检查失败 | 停止，不启动 API/Vite |
| 发现上次失败/中断标记 | 停止自动重试，要求检查数据库和备份 |

可使用 `python start.py --no-auto-migrate` 只检查版本；存在待执行迁移时停止。该模式也不会创建缺失的 SQLite 数据库。

**新迁移的开发规则**

新增 Alembic 模板默认 `startup_safe = False`。开发者需验证旧数据兼容性、执行时长、锁影响和备份恢复，评审后才能将纯新增、可控的迁移标记为 True。该标记是一项可信代码评审声明，不能阻止一个错误标记或恶意修改过的脚本执行任意 Python/SQL；源代码、镜像和迁移文件必须来自可信来源。

当前 `0018` 新增索引、`0019` 新增污水监测表、`0020` 新增接警来源关系、`0021` 新增账号管理和角色配置，均已标记可在本地停服启动时执行。`0021` 保留旧账号的业务操作范围，不自动授予普通账号管理权限。`0017` 转换 SQLite 历史重量、`0015/0016` 涉及账号/组织数据等迁移维持手动。已有库若尚在 `0016`，第一次仍需停服并运行 `python migrate.py`；之后经审核标记的新迁移才可自动执行。不要修改已发布迁移的 SQL 来触发重跑，应新增 revision。

**锁、备份与失败处理**

- SQLite 使用数据库旁的操作系统文件锁；PostgreSQL 使用会话级 advisory lock，并让 Alembic 复用持锁的连接。默认等待 30 秒；进程退出时锁释放，不通过删除锁文件抢锁。
- PostgreSQL 自动迁移发现旧服务/其他数据库客户端连接时拒绝执行；迁移期间对现有 public 表取得 SHARE 锁以阻止并发写入，锁等待上限 5 秒，迁移语句上限 10 分钟。原有服务和其他写入程序仍应提前停止；迁移锁是协作协议，绕过受控入口的 SQL/DDL 不受它强制保护。
- SQLite 使用在线备份 API 生成一致副本并执行完整性检查；PostgreSQL 使用与服务器相同主版本的 `pg_dump -Fc`。支持 PATH、`WELLSPRING_PG_BIN`，Windows 还检查 `Program Files/PostgreSQL/<主版本>/bin`。找不到客户端、磁盘/权限不足、超时等均阻止迁移。密码只通过子进程环境传入，不打印或放在命令行。
- 备份默认保存在 `backend/backups/startup/`，每次待执行升级生成独立文件及 JSON（数据库位置、源/目标版本、SHA-256），不覆盖旧备份、不自动删除。文件属于数据库数据，应限制目录 ACL、监控磁盘容量并按单位要求保留。备份成功不等于已完成业务恢复演练。
- DDL 前持久化失败标记，提交成功后移除；SQLite 标记位于数据库旁，PostgreSQL 标记位于备份目录。中断后不要盲目删除标记或只回滚程序版本。检查备份、迁移日志和实际结构，必要时恢复；显式 `python migrate.py` 代表人工检查后继续执行，成功后清理标记。数据库已经到 head 时，显式手动命令也会在核对版本后清理标记。
- PostgreSQL 当前迁移使用同一事务执行本次升级；未来若需要 `autocommit_block`/并发建索引等事务外操作，应使用独立人工发布流程，不标为启动安全。SQLite 不能保证所有 DDL 的失败都完整回滚。`0017` 本身不支持有损降级，迁移失败不会自动恢复或自动降级，以免覆盖新的写入。

**部署边界**

此行为只接入本地开发启动器。直接运行 Uvicorn 和离线应用容器不会自行改表；离线部署继续使用持有迁移所有者凭据的独立 `migrate` 步骤，应用运行角色不增加 DDL 权限。正式部署可由发布编排实现“迁移成功后启动应用”，但仍应由单独的一次性任务完成，并提前验证停写、兼容性和恢复。

本次验证仅使用合成 SQLite 与新建的隔离 PostgreSQL 测试库，未执行用户现有数据库的自动迁移。回归覆盖真实备份、版本更新、幂等重启、备份失败、执行失败及中断保护、文件锁/数据库锁竞争、其他客户端连接拒绝、未知版本/分支/无版本库保护、新安装与迁移模板默认值。
